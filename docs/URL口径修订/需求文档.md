## 一、背景

`rehype-safe-urls` 把协议校验从「`Card`/`File` 属性」扩大到**所有元素的 `href` / `src`** 之后，`isSafeHref` 的旧口径（仅 `#`、`/` 开头、http(s)/mailto/tel）开始误伤日常写法。

实测（`MarkdownRenderer` 渲染后核对产物）：

| 写法 | 现状 | 期望 |
|---|---|---|
| `https://…`、`http://…`、`mailto:`、`tel:` | 原样输出 | 不变 |
| `/uploads/a.png`（站内绝对路径） | 原样输出 | 不变 |
| `#section`（锚点） | 原样输出 | 不变 |
| `uploads/a.png`、`./uploads/a.png`、`../a.png` | **降级为 `#`** | 放行 |
| `//cdn.example.com/a.png`（协议相对） | **降级为 `#`** | 放行 |
| `?page=2`（纯查询） | **降级为 `#`** | 放行 |
| `example.com/a`（无 scheme，浏览器按相对路径处理） | **降级为 `#`** | 放行 |
| `javascript:`、`vbscript:` | 拦截 | 继续拦截 |
| `data:`、`blob:`、`file:` | 拦截 | **继续拦截**（本次不放行） |
| `ftp:`、`chrome:` 等其它 scheme | 拦截 | 继续拦截 |

## 二、根因

`src/internal/url-policy.ts` 的判定是"白名单列前缀"：

```ts
if (/^#/.test(raw)) return true;
if (/^\/(?!\/)/.test(raw)) return true;          // 只认以 / 开头的相对路径
if (/^(?:https?:|mailto:|tel:)/i.test(raw)) return true;
return false;                                     // 其余一律拒
```

缺了「无 scheme 的相对引用」与「协议相对 `//host`」两类。

## 三、修法（单点、单文件）

改成"先认危险/未知 scheme，其余无 scheme 一律放行"：

```ts
export function isSafeHref(href: string): boolean {
  const raw = (href ?? "").trim().replace(/^[\u0000-\u001f\s]+/, "");
  if (!raw) return false;
  // 1. 白名单 scheme
  if (/^(?:https?|mailto|tel):/i.test(raw)) return true;
  // 2. 其它任何 scheme 一律拒（javascript / data / blob / file / ftp / chrome …）
  if (/^[a-zA-Z][a-zA-Z0-9+.-]*:/.test(raw)) return false;
  // 3. 无 scheme：锚点、纯查询、相对路径、站内绝对路径、协议相对 //host 都放行
  return true;
}
```

要点：
- 第 2 步是安全关键——`javascript:alert(1)`、`data:text/html;…`、`blob:…` 都带 scheme，一律被拦；
- `//host/path` 不带 scheme，走第 3 步放行。它与 `https://host/path` 在浏览器里等价（继承页面协议），不引入新风险；
- `example.com/a` 同理放行——浏览器本就按相对路径解析，拦它反而让作者困惑。

## 四、影响面

| 面 | 影响 |
|---|---|
| 闸门 `rehype-safe-urls` | 相对路径图片/链接恢复正常 |
| 组件兜底（`Card`/`File`/`Image`） | 同一函数，口径自动一致 |
| 诊断 `UNSAFE_HREF` | 相对路径不再报；`javascript:` 等仍报 |
| 宿主 `blog-heikeson2026` | **零改动**。其 `lib/url-policy.ts` 服务友链、朋友圈、图库、右键菜单等自有场景，与 Markdown 渲染互不依赖 |
| 往返（`md → AST → md`） | 不受影响（只改渲染期属性） |

## 五、顺带修正的注释

`src/internal/url-policy.ts` 头部现写着「判定口径与宿主 `lib/url-policy.ts` 保持一致，改动须同步两边」——这是本包还住在宿主 monorepo 时的约定，已过时。改为：

> 宿主另有一份 `lib/url-policy.ts`，服务友链/图库/右键菜单等站点自有场景，与本包互不依赖；本文件是 Markdown 渲染的唯一口径。

## 六、验收

- [ ] `uploads/a.png`、`./a.png`、`../a.png`、`//cdn.example.com/a.png`、`?page=2`、`example.com/a` 六类**原样输出**
- [ ] `javascript:`、`data:`、`blob:`、`ftp:` 四类仍被拦截（链接改 `#`、图片移除属性）
- [ ] `<Image src="uploads/a.png">` 正常渲染 `<img>`；`<Image src="javascript:…">` 仍不渲染
- [ ] 诊断：相对路径零诊断；`javascript:` 仍报 `UNSAFE_HREF`
- [ ] `dev/fixtures`：`containers`、`kitchen-sink` 保持 strict 往返；`edge-cases` 剩余差异仍只有降级内容
- [ ] `npm run typecheck` / `build` / `pack` 通过，发布清单不变

## 七、明确不做

- 不放行 `data:`（含 `data:image/svg+xml` 的 XSS 风险），粘贴 base64 图的场景后续单独评估。
- 不放行 `file:`、`ftp:`、`chrome:` 等其它 scheme。
- 不改宿主任何文件。
