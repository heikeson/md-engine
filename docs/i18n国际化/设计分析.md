## 一、业界四种流派

| 流派 | 代表 | 注入什么 | 默认语言 | 缺失回退 | 内置 `t()` |
|---|---|---|---|---|---|
| **locale 字符串** | React Aria `I18nProvider` | `locale: string` | 跟随浏览器/系统，Provider 是**覆盖**手段 | 语言族截断 | 否（字典在包内，另提供 formatter hooks） |
| **语言包对象（整包）** | antd `ConfigProvider locale={zhCN}` | 完整 locale 对象 | 包内默认（antd 为 en_US） | 无 Provider 则用默认包 | 否 |
| **语言包对象（可部分）** | antd-mobile `mergeLocale(base, {...})` | Partial 包 | base | 未译字段**继承 base** | 否 |
| **领域层 code + 文本接管** | Zod 4 `z.config({ customError(iss) })` | 错误映射回调 / locale 包 | 包内英文 | 全局 < schema 级 < 每次解析 | 否 |

四个案子的共同点，恰好是四条可以直接搬过来的结论：

1. **文案字典与 locale 是两件事**。React Aria 的 Provider **只管 locale**，一个翻译字符串都不接——因为 locale 还要驱动日期、数字、列表连接词、排序、书写方向。反过来 antd 只接字典、不管方向。本包两者都需要（既要译文，也要 `Intl` 格式化与 RTL）。
2. **库必须自带一份完整默认文案**，不能要求宿主全量翻译才可用。
3. **库不自建翻译框架**。四个案子没有一个在库内实现复数、命名空间、插值运行时；它们把字典当数据，把文本生成权交给调用方或展示层。
4. **缺失回退是硬要求**，antd-mobile 明确"未覆盖字段继承 base，新建语言包无需逐条翻译"。

## 二、三条公理（判断"是否打补丁"的判据）

### 公理一：一条消息 = 一个完整语义单元

FormatJS/ICU 文档在富文本一节的原话是：把尽可能多的文本放进一条消息，*"so sentences don't have to be broken up into chunks"*。理由很硬：拆句后译者无法调整语序。

本包现有两处正好违反：

| 键 | 现状 | 英文的必然结果 |
|---|---|---|
| `editorWordCountUnit: "字"` | 代码拼 `{n} {unit}` | `3 words` 拼得出来，`1 word` 拼不出来（单复数） |
| `editorDiagnosticPrefix: "条提示："` | 代码拼 `{n} {prefix}{msg}` | 中文"3 条提示："→ 英文得是 `3 issues:`，语序与标点都变 |

**推论：不是"支持插值"就够了，必须支持复数。** 这正是我初版判断错的地方（见 §六）。

### 公理二：领域层不产出人类文本

`src/policy.ts`、`src/policy-tags.ts` 是纯函数，没有 React 上下文，现在把 9 条中文模板串就地拼好塞进 `Diagnostic.message`。Zod 4 把同类问题收敛成了标准范式：

- issue 是**判别联合**，用 `code` 区分（`invalid_type` / `too_small` / …）
- 文本由 `customError(iss)` 或 locale 包生成，**调用方可以完全接管**
- `message` 仍然保留，作为"人类可读"的现成产物（日志、无 UI 场景）

本包的 `Diagnostic` **已经有 `code` 了**（`src/policy.ts:29-38`），比当年的 Zod 起点更好。缺的只是**插值参数**——没有 `params`，展示层拿到 `DEPTH_EXCEEDED` 也造不出"第 3 层容器 X 超出上限 2"。

### 公理三：locale 是显式受控输入，库内无全局可变状态

- React Aria 的 Provider 定位是"覆盖浏览器/系统默认"，因为**用户偏好必须优先于系统语言**，且服务端没有 `navigator`。
- locale 协商的业界次序是 **URL > Cookie > Accept-Language 头**；`localStorage` 只允许作为非 SSR 场景的兜底，绝不能驱动首屏服务端输出。服务端与客户端解析出不同 locale，就是 hydration mismatch。
- MDN 对 `Intl.PluralRules` 的建议同样明确：**应显式传入应用 UI 语言并附带回退语言，不要依赖运行时默认 locale**。

**推论：`registerLocale()` 这种 module 级可变注册表是反模式。** 服务端多请求并发时，不同语言的请求会互相污染同一个全局字典；而且它让"某语言是否可用"变成隐式状态，无法在代码里追踪。这也是我初版判断错的地方（见 §六）。

## 三、本包的设计

### 3.1 暴露面：两个维度，各司其职

```ts
interface RenderConfig {
  /** 内置语言选择 + 驱动 Intl 格式化与书写方向。BCP-47，默认 "zh-CN" */
  locale?: string;
  /** 逐键覆写，最高优先级。宿主自定义语言包也走这里 */
  messages?: UITextPatch;
}

interface EditorConfig extends /* … */ {
  locale?: string;
  messages?: UITextPatch;
}
```

为什么是两个字段而不是一个：

- `locale` 回答"**默认用哪套**，以及日期/数字/复数规则按哪种语言算，排版朝哪边"。它是**行为开关**。
- `messages` 回答"**个别词怎么改**"。它是**数据补丁**。
- 合成一个字段的后果：只改一个词的宿主必须传整个语言对象（antd 流派的痛点）；只想切语言的宿主得自己找包（React Aria 流派的痛点）。两者并存不是冗余，是覆盖两个正交需求。

现有 `config.text` 保留为 `messages` 的**别名**（`text` 优先级与语义完全不变，`messages` 是新增的正名），避免破坏 C2。

### 3.2 解析链

```
messages[key]                              ← 最高：宿主逐键覆写
  ↓ 缺
内置包[locale][key]                         ← 内置 zh-CN / en-US 全量
  ↓ 缺（locale 未内置）
内置包[截断 locale][key]                     ← en-GB → en → zh-CN
  ↓ 缺
内置包["zh-CN"][key]                        ← 最终兜底，永不 undefined
```

内置包用 `satisfies UIText` 保证**编译期全量**；宿主 `messages` 是 `Partial`，靠回退链补齐（对应 antd-mobile 的 base 继承思想，但用类型系统而非 `mergeLocale` 运行时合并来保证）。

**不做** `navigator.language` 探测。提供无副作用的 `detectLocale()` 供宿主在 `useEffect` 里调用，或用 `resolveLocale(acceptLanguageHeader)` 在服务端解析——决策权在宿主，因为它才知道 URL/Cookie 的优先级。

### 3.3 消息语法：ICU MessageFormat

采用 ICU 语法而不是自研 `{n}` 插值，理由是需求本身逼出来的：

```ts
// zh-CN
editorWordCount:      "{n, plural, other {# 字}}"
editorDiagnostic:     "{n, plural, other {# 条提示：}}{first}"
// en-US
editorWordCount:      "{n, plural, one {# character} other {# characters}}"
editorDiagnostic:     "{n, plural, one {# issue} other {# issues}}: {first}"
```

收益：

- 复数规则与 CLDR/ICU 同源，`Intl.PluralRules` 只负责判定类别，**规则数据不用自己维护**（中文只有 `other`，英文有 `one`/`other`，阿拉伯语有 6 类）。
- 消息可被 CAT 工具（Lokalise / Crowdin）直接处理，译者改语序不用碰代码。
- 宿主若已在用 `react-intl`，消息格式**完全一致**，可以复用同一份翻译记忆库与同一批译员。

实现选择：`intl-messageformat`（FormatJS，与 ICU 规范同源、带 AST 缓存），而不是手写解析器。手写解析器的隐性成本是复数分支、`#` 占位符、嵌套消息、引号转义四条边界，长期维护不划算。

> 需要显式记录的风险：Node 若是 **small-icu** 构建，缺 locale 数据，`Intl` 会静默回退到 `en-US`。本包应在入口处用 `Intl.PluralRules.supportedLocalesOf(locale).length` 做一次判定，不支持时降级到内置包 + `en-US` 规则，并在开发模式告警。

### 3.4 书写方向：被忽略的另一半

i18n 不只是文字。React Aria 的做法是**从 locale 推导 direction**，不单独给 prop；Proper UI / AWC UI 的做法是"组件样式一律用 CSS 逻辑属性，`dir` 只在根节点设一次"。

本包的现状是**样式随包走**（C3），所以这一条必须算进本次范围——`styles/` 下有 **18 处物理方向属性、横跨 9 个文件**（`margin/padding/border-left|right`、`text-align: left|right`、`left:`/`right:`）。这些在 `dir="rtl"` 下全部错位，光加语言包等于交付一个阿拉伯语下崩坏的组件库。

设计：

- `locale` → `direction`（`ar` / `he` / `fa` / `ur` 为 RTL，其余 LTR），经 Provider 下发，组件根元素按需输出 `dir`；宿主 `<html dir>` 仍是首选控制点，库内输出只是兜底。
- `styles/` 物理属性迁移为逻辑属性（`margin-inline-start`、`padding-inline-end`、`border-inline-start`、`text-align: start`、`inset-inline-start`）。
- **例外**：Mermaid 图表内容**不镜像**——图是用户的数据，不是 UI 镜像对象。缩放按钮等外围控件跟随方向。
- 图标镜像（如箭头）只针对方向性图标，`Callout` 的类型图标不镜像。

### 3.5 诊断：补 `params`，细分 `code`

```ts
export interface Diagnostic {
  code: DiagnosticCode;                             // 已是消息键
  level: "warn" | "error";
  line: number;
  message: string;                                  // 保留：中文兜底 / 日志 / 无 Provider
  params?: Record<string, string | number>;          // 新增
  range?: [number, number];
}
```

同时修掉一个粒度错配：`DUPLICATE_ID` 现在对应两条不同文案（`policy-tags.ts:129` 与 `:136`），违反"一个 code 一条消息"。拆为 `DUPLICATE_ID_ANCHOR` / `DUPLICATE_ID_DIV`，旧码保留在联合类型中但不再产出。

展示层（`MarkdownEditor.tsx` 状态栏、`dev/chrome.tsx`）规则：有对应 locale 消息 → 用 `code + params` 渲染；否则回退 `message`。领域层（`parse` / `policy` / `serialize`）**不 import 任何文案表**，保证解析结果与语言无关、可缓存、可跨语言复用。

### 3.6 键的形态：沿用扁平 camelCase

`UIText` 现有 33 键是扁平 camelCase（`mermaidZoomIn`、`editorWordCountUnit`）。新键继续用**前缀式扁平命名**（`diagDepthExceeded`、`calloutNote`、`typeTableAttr`），不改成 `mermaid.zoom.in` 点分嵌套。

理由：键名是对外契约（C2），改名即破坏；点号嵌套还会让 `Partial` 逐键覆盖变成深合并问题（antd 整包替换就是为了绕开它）。扁平 + 前缀已能表达分组，且 `keyof` / `satisfies` 推导最直接。

### 3.7 旧碎片键的收口

`editorWordCountUnit` / `editorDiagnosticPrefix` 按公理一应废弃，但删键违反 C2。处理方式：

- `editorWordCount` / `editorDiagnostic` 为**新正键**，`UIText` 里旧键标注 `@deprecated`。
- 过渡期单向投影：宿主只覆写了旧键、未覆写新键时，用旧键值代入 `{unit}` / `{prefix}` 组装，输出与现状逐字一致。
- 下一个大版本移除旧键。**单轨**：不存在"新旧两套并行渲染逻辑"。

## 五、明确不做（每条都是判断，不是遗漏）

| 不做 | 理由 |
|---|---|
| 翻译语法标识符（`Callout` / `Tabs` / `H2`） | 它们是 Markdown 源码里的标识符，译成"标注"后按钮与源码对不上。只本地化描述（`插入 {name}`） |
| 加 Callout 那 11 个类型标题键 | `TYPE_MAP[].label` 是死数据，渲染从不读取。不启用默认标题就不加键，避免语言包积累永不生效的条目 |
| `registerLocale()` 全局注册表 | SSR 多请求并发污染；隐式全局状态不可追踪（§二 公理三） |
| `navigator.language` 自动探测 | 服务端无 `navigator`；SSR/CSR 不一致即 hydration mismatch |
| 传入 `t()` 函数而非字典 | 字典是数据（可序列化、可缓存、可跨 RSC 边界），函数是行为（破坏 memo 稳定性与序列化） |
| 库内实现翻译工作流（命名空间、按需分包、语言切换器） | 那是宿主 i18n 框架的职责 |
| 本期做 `site/` 文档站 | 站点需要的是**路由级** i18n（`/en/` 路径、切换器、SSG 双语预渲染、`hreflang`），与引擎的消息层是两个问题 |

## 六、被调研推翻的两处初版判断

| 初版判断 | 调研证据 | 修正 |
|---|---|---|
| 自写 30 行 `{n}` 插值即可 | FormatJS ICU 规范：复数/`#`/嵌套/转义；`Intl.PluralRules` 说明 `n === 1` 硬编码在多语言下必然错 | 改用 ICU MessageFormat + `intl-messageformat`，复数走 CLDR 规则 |
| 提供 `registerLocale()` 注册表 | MDN 明确"显式传入 locale 与回退链，不依赖运行时默认"；locale 协商资料指出全局/隐式状态是 SSR 与一致性的根源 | 取消全局注册表，改为 `locale` + `messages` 两个受控输入 |

## 七、验收思路

- **完整性**：内置语言包键集合 ≡ `UIText` 键集合（`satisfies` 编译期强制，另加运行期断言）。
- **零回归**：默认 locale 下 `npm run snapshot` 与现状逐字一致。
- **无漏网中文**：切 `en-US`、正文用纯英文样例，扫描渲染结果中的中文，命中即失败。
- **语法零污染**：同一 Markdown 在不同 `locale` 下 `parse()` 与 `roundtrip()` 输出完全相同。
- **复数正确**：`n = 0 / 1 / 2` 三档断言中英文各自形态。
- **RTL**：`dir="rtl"` 下截图比对，确认无左右错位；`ltr` 下像素级不变。
- **SSR**：`renderToString` 不触碰 `window`/`navigator`；同 locale 下服务端与客户端输出一致；small-icu 场景降级不崩。
