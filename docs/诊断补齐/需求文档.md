## 一、现状（实测）

| 输入 | 渲染结果 | 诊断 |
|---|---|---|
| `<File href="javascript:alert(1)" />` | `href` 被 `isSafeHref` 拦掉，不可点击 | **无** |
| `<Card href="javascript:alert(1)" />` | 同上 | **无** |
| `<Image src="javascript:alert(3)" />` | `src` **未过白名单**，直接进 `<img src>`；由 React 19 在渲染期替换成抛错 URL 兜底 | **无** |
| `[a](javascript:alert(1))`、`![x](javascript:alert(2))` | 普通 Markdown 链接/图片同样不过白名单，同样靠 React 19 兜底 | **无** |
| `<FooBar>正文</FooBar>` | 标签回退为文本，正文保留（符合「不吞内容」） | **无**（`UNKNOWN_TAG` 未产出） |

代码事实：

- `DiagnosticCode` 里声明了 4 个码，实际只产出 `UNCLOSED_TAG`、`DEPTH_EXCEEDED`；
- `isSafeHref` 仅被 `components/cards.tsx`、`components/file.tsx` 使用，`components/image.tsx` 没有；
- `parse()` 里没有任何遍历 `attributes` 或 mdast `link`/`image` 的 URL 校验。

> 为什么现在没出事：React 19 渲染期会把 `javascript:` URL 替换成抛错 URL。但这是**消费方框架**的兜底，不是引擎契约；一旦宿主覆盖 `a`/`img` 组件（它确实覆盖了 `a`）、或把 HTML 交给别的运行时，风险就回到真实。契约 C1 写明"外链必须过 `isSafeHref`"，当前实现不满足。

## 二、目标

1. `UNSAFE_HREF` 真正产出：容器属性（`href` / `src`）与 Markdown 链接/图片的非法协议都要报，定位到行。
2. `Image.src` 走 `isSafeHref`，与 `Card` / `File` 口径一致（渲染层降级）。
3. `UNKNOWN_TAG` 真正产出：写了一个不在 `registry` 里的容器名时给出提示，**不改变渲染行为**（仍回退为文本）。
4. 不新增运行依赖、不改既有渲染结构、不破坏 `md → AST → md` 往返。

## 三、方案

### 3.1 URL 校验（UNSAFE_HREF）——诊断 + hast 层唯一闸门

**诊断**（告诉作者哪里有问题）：

| 检查对象 | 位置 | 处理 |
|---|---|---|
| 容器属性 `href` / `src` | `jsxBlock.attributes` | 非法 → `UNSAFE_HREF` |
| Markdown 链接 / 图片 | mdast `link` / `image` 的 `url` | 非法 → `UNSAFE_HREF` |

**降级（根治点）**：在 `remark-rehype` 之后、其余 rehype 插件之前插入 `rehypeSafeUrls`，
遍历所有 hast 元素，把非法 `href` 改写为 `#`、非法 `src` 删除。放在这一层的理由：

1. 一处覆盖全部来源：容器属性、普通链接/图片、宿主 `remarkPlugins` 生成的节点；
2. **宿主用 `RenderConfig.components` 覆盖 `a` / `img` 也拿不到危险地址**——闸门在组件之前，
   不需要宿主"自己记得校验"，因此不必在契约里加约束；
3. 与诊断共用 `isSafeHref`，不会出现两套判定漂移。

组件内的 `isSafeHref`（`Card` / `File` / `Image`）保留为兜底：它们可能被直接当 React 组件使用，
不经过渲染管线。但它不再是安全边界。

### 3.2 未知标签（UNKNOWN_TAG）

`jsx-flow` 只识别注册名，未知标签落到 mdast `html` 节点。因此：

1. 遍历 `html` 节点，取 `^<([A-Z][A-Za-z0-9]*)`；
2. 名字不在 `registry`（`COMPONENTS` + `ITEMS`）里 → 报 `UNKNOWN_TAG`，带行号；
3. 渲染行为不变（还是回退文本）。

误报控制：`html` 节点天然不含围栏代码块内容；仍是 HTML 块的大写标签（如 `<Details>`）会被报——这正是想要的提示；若后续发现噪音，可加"仅当相邻出现 `</Name>` 才报"。

### 3.3 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | policy 出诊断 + 渲染层统一 `isSafeHref` | 诊断可见、降级一致、无新依赖 |
| B | 只补 `Image` 的 `isSafeHref` | 修一半：无诊断，Markdown 链接仍不过白名单 |
| C | 引入 `rehype-sanitize` 全量消毒 | 会重写渲染输出（删属性、改标签），与「语法只增不改」冲突，且体积大 |

## 五、风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 诊断噪音 | 作者在正文里贴 `<Details>` 之类的 HTML 会被报 `UNKNOWN_TAG` | 先按上述规则执行；若确实吵，再加"必须成对出现"的收敛条件 |
| 渲染层替换 url 影响往返 | 只改 hast/属性，不改 mdast，`md → AST → md` 不受影响 | 验收里加 `kitchen-sink` strict 仍通过 |
| 诊断数量变化影响编辑器状态栏 | 宿主会看到更多提示 | 属预期；`level` 用 `warn`，不阻断输入 |
| 与宿主覆盖组件冲突 | 宿主覆盖 `a` 后可能绕过降级 | 在 `RenderConfig` 文档里写明：覆盖 `a`/`img` 时必须自行调用 `isSafeHref` |

## 六、验收

- [ ] `<File href="javascript:…" />`、`<Card href="javascript:…" />`、`<Image src="javascript:…" />` 三类均产出 `UNSAFE_HREF`，渲染不可点击/不可加载
- [ ] `[a](javascript:…)`、`![x](javascript:…)` 产出 `UNSAFE_HREF`，渲染后 `href`/`src` 为 `#`
- [ ] `<FooBar>正文</FooBar>` 产出 `UNKNOWN_TAG`，正文仍保留、标签不泄漏
- [ ] 合法内容（`https:` / `mailto:` / 站内相对路径）零诊断
- [ ] `dev/fixtures` 三篇：`containers`、`kitchen-sink` 往返仍 strict 通过
- [ ] `npm run typecheck` / `build` / `pack` 全部通过，发布清单不变

## 七、明确不做

- 不做 HTML 全量消毒（`rehype-sanitize`），不改渲染标签结构。
- 不为 `icon`、`align` 等非 URL 属性做校验。
- 不改"未知标签回退为文本"的既有行为。

### 8.3 口径说明

- 安全边界在 **hast 闸门**：宿主覆盖 `a` / `img`、注入 `rehypePlugins` 都不影响结论，无需在契约里额外约束宿主。
- 诊断只报**内容里的非法地址**；宿主插件自己生成的地址会被闸门降级，但不产生诊断（那是宿主代码，不该由内容诊断背锅）。
- 组件内的 `isSafeHref` 仅作兜底（组件被直接当 React 组件用时生效），不是安全边界。
