## 一、结论先行

**可行，且属于低成本增强。** 但"直接引入一个文件类型图标库"这个动作本身不推荐，推荐的做法是「**映射表 + 既有 lucide 图标**」：

| 优先级 | 做法 | 依赖变化 | 体积增量（估算/实测） |
|--------|------|----------|----------------------|
| P0 | 扩展名 → 映射表 → 复用已安装的 `lucide-react` 图标，未知类型回退现有 `FileIcon` | **零新增依赖** | 单图标源码 0.8–1.0 KB；取 10 个约 9 KB（gzip ≈ 3 KB） |
| P1 | 支持 `<File icon="md" />` 显式覆盖（默认形态给 `icon="auto"`） | 零依赖，仅 registry 登记 | 0 |
| 不推荐 | 接入 `material-icon-theme` / `@iconify-json/vscode-icons` / `file-icons-js` 等整套主题或字体方案 | 新增 1 个依赖 + 数据/字体资产 | 数据量级 10²–10³ 个多色 SVG，与"样式随包、单色随主题"的现有约束冲突 |

一句话：**图标来源不缺，缺的是"克制的一层映射"**。用 lucide 现成图标即可覆盖 90% 的写作场景，不必为"全类型覆盖"付整套主题的代价。

## 二、现状事实（已核验）

### 2.1 渲染层

```1:38:src/components/file.tsx
export default function File({ name, href }: FileProps) {
  const safeHref = href && isSafeHref(href) ? href : undefined;
  return (
    <div className="files-row files-file-row">
      <span className="files-spacer" aria-hidden="true" />
      <FileIcon />
      ...
```

- `<File>` 只有 `name` / `href` 两个属性，图标固定为 `FileIcon()`，**与 `name` 完全无关**。
- `FileIcon` 是自绘 16×16 SVG（`fill currentColor opacity=0.25` + `stroke currentColor`），即"双色调"风格；`FolderIcon` 同为双色调。
- 状态类的形态切换已由 `docs/文件夹图标开合形态.md` 落地（闭合/敞口双形态，纯 CSS 切换），本议题与之无冲突。

### 2.2 属性管线是开放字典（关键利好）

| 环节 | 代码 | 行为 |
|------|------|------|
| 词法 | `src/syntax/jsx-mdast.ts` `ATTR_RE` | 任意 `key="value"` / 布尔 key 都能进 `attributes` 字典 |
| 节点 | `JsxBlock.attributes: Record<string, string \| boolean>` | 不校验属性名 |
| 序列化 | `handleJsxBlock` → `serializeAttributes` | 逐项写回，顺序保持 |
| 渲染 | `jsxBlockToHast` | 属性原样转 `properties`，最后交给组件 props |
| 诊断 | `src/policy-tags.ts` | 只校验 `href` / `src` 协议，**不校验属性名白名单** |

结论：新增 `icon` 属性**不会**破坏往返一致性（`md → AST → md` 仍逐字一致），改动面只有 `registry.ts`（登记便于编辑器/文档）与 `file.tsx`（消费）。

### 2.3 依赖与构建

- `lucide-react@1.61.0` 已是 **`dependencies`**，并在 `tsup.config.ts` 的 `external` 列表中（不重复打包，由宿主解析）；`callout.tsx` / `acc-item.tsx` 已在用。
- 已核验 `lucide-react.d.ts` 中存在本次需要的图标：`FileCode` / `FileText` / `FileImage` / `FileJson`(别名) / `FileBraces` / `FileCog` / `FileLock` / `FileArchive` / `FileSpreadsheet` / `FileTerminal` / `FileType` / `FileKey` / `FileDiff` / `FileChartColumn` 等。
- 实测：`node_modules/lucide-react` 安装体积 34.7 MB / 4388 文件——**这是安装体积，不是产物体积**；产物只包含被 import 的单图标文件（`file-code.mjs` 820 B、`file-image.mjs` 855 B、`file-lock.mjs` 866 B……）。
- 图标是 `currentColor` 单色描边，天然跟随 `.files-row` 的 `text-muted-foreground` / `hover:text-foreground`，**暗色主题零额外处理**。

### 2.4 契约约束（不可破坏）

| 约束 | 内容 | 对本议题的影响 |
|------|------|----------------|
| C1 语法只增不改 | 已有写法必须继续有效 | 新增 `icon` 属性属"只增"，合法；不写时行为与今天完全一致 |
| C2 配置只增不改 | 渲染配置项只追加 | 若加 `config.fileIcons?: boolean` 属只增 |
| C3 样式随包走 | `styles/engine.css` 由宿主 Tailwind 处理 | 图标必须能靠类名 + `currentColor` 生效，**不能依赖新增字体文件或外链 CSS** |
| SSR 安全 | 渲染层不访问 window/document | 图标必须静态内联 SVG；`fetch` 图标集方案直接排除 |
| 零客户端 JS | `<Files>` 用原生 `<details>`，无 hydration | 映射必须纯函数、渲染期完成，不能靠 effect 检测扩展名 |
| 构建产物发布 | `files` 白名单仅 `dist` / `styles` / README / 契约 / LICENSE | 图标不能以"用户自行拷贝资产"的形式分发 |

## 三、候选方案对比

| 方案 | 来源 | 新增依赖 | 覆盖度 | 视觉一致性 | 暗色/主题 | 工作量 | 主要风险 |
|------|------|----------|--------|------------|-----------|--------|----------|
| **A. lucide 映射（推荐）** | 已装的 `lucide-react` | 无 | 中高（单色 File* 系列约 30 种） | 与现自绘双色调**有差异**，需统一口径 | 优（`currentColor`） | 0.5 人日 | 图标区分度靠形状，16px 下 `FileCode`/`FileText` 差异偏小 |
| **B. 自绘双色调扩展** | 手写 SVG | 无 | 看投入（每类 1 个 path） | **最优**（与 FileIcon/FolderIcon 同风格） | 优 | 1.5–2 人日（10–15 类） | 需设计成本，长期维护靠人 |
| **C. 整套图标主题数据** | `material-icon-theme` / `@iconify-json/vscode-icons` | +1 | 极高（数百类） | 多彩，与现有单色体系割裂 | 差–中（多彩需两套变体） | 2–3 人日（含抽取/裁剪脚本） | 体积（数据量大）、许可声明、与 C3 冲突、暗色对比度 |
| **D. 字体图标库** | `file-icons-js` / `file-icon-vectors` | +1 | 高 | 取决于字体风格 | 中（`color` 可控） | 1–2 人日 | 需字体文件 → 与 C3「样式随包」冲突；FOUT；`@font-face` 需宿主配合 |
| **E. 属性覆盖（正交）** | `<File icon="ts" />` | 无 | 由作者决定 | 可控 | 优 | 0.2 人日 | 与 A 叠加使用效果最好；需 registry 登记 |

**淘汰理由速记**

- C：方案本身成熟（VS Code 图标主题，MIT），但它是"主题"而非"图标组件"——一套 JSON 映射 + 数百个多色 SVG + light/dark 两套变体。本包是**库**，产物要能塞进宿主 chunk，且样式契约要求随包走；把 10²–10³ 个 SVG 内联进 `dist` 与"轻量渲染引擎"的定位相悖。（数据量级为包形态的通用认知，本仓库未安装实测，若进入 P2 阶段需先量化。）
- D：字体方案要么宿主额外配 `@font-face`（违反 C3），要么把字体放进 npm 包（`files` 白名单需放行二进制资产，且首屏 FOUT）。对"文件树图标"这种小需求不划算。
- B：视觉最统一，但成本是 A 的 3–4 倍，且扩展新类型需要改代码 + 改设计。适合在 A 上线后、对特定高频类型（`.ts` `.md` `.json`）做补强。

## 四、推荐方案（A + E）

### 4.1 形态

```md
<Files>
<Folder name="src" defaultOpen>
<File name="index.ts" />          ← 自动按扩展名取图标
<File name="README.md" />
<File name="data.json" />
<File name="logo.svg" />
<File name="notes" />             ← 无扩展名 → 回退通用 FileIcon
<File name="x.custom" icon="none" />  ← 显式关闭图标
</Folder>
</Files>
```

### 4.2 映射表草案（18 类，覆盖真实文章场景）

| 扩展名 | lucide 图标 | 语义 |
|--------|-------------|------|
| `ts` `tsx` `js` `jsx` `mjs` `cjs` `vue` `svelte` `go` `py` `rs` `java` `c` `cpp` `h` | `FileCode` | 源码 |
| `md` `mdx` `txt` `rst` | `FileText` | 文档 |
| `json` `jsonc` `yaml` `yml` `toml` `ini` `env` | `FileBraces`（或 `FileCog`） | 数据/配置 |
| `css` `scss` `less` | `FileType` | 样式 |
| `html` `htm` | `FileCode`（复用） | 标记 |
| `png` `jpg` `jpeg` `gif` `webp` `avif` `ico` `bmp` | `FileImage` | 图片 |
| `svg` | `FileImage` | 矢量图 |
| `mp4` `webm` `mov` | `FileVideo` | 视频 |
| `mp3` `wav` `flac` | `FileAudio` | 音频 |
| `zip` `tar` `gz` `7z` | `FileArchive` | 归档 |
| `csv` `xlsx` `xls` | `FileSpreadsheet` | 表格 |
| `sh` `bash` `zsh` `ps1` `bat` | `FileTerminal` | 脚本 |
| `lock` | `FileLock` | 锁文件 |
| `pem` `key` `crt` `p12` | `FileKey` | 密钥 |
| `woff` `woff2` `ttf` `otf` | `FileType`（复用） | 字体 |
| `sql` `db` `sqlite` | `FileDiff` 或 `Database` | 数据库 |
| `pdf` | `FileText`（复用） | 电子文档 |
| 其他 / 无扩展名 | `FileIcon`（现有自绘） | 通用 |

规则细节：

- **取最后一个点之后的小写扩展名**；`name` 缺失或仅 `.gitignore` 这类"点开头无扩展名" → 走 `FileIcon`。
- 大小写不敏感（`README.MD` 同样命中）。
- 映射表放 `src/components/files-icons.tsx` 内的一张 `Record<string, IconComponent>`，**不做运行时动态 import**（保持 SSR + 零 JS）。

### 4.3 为保证视觉不超过现有风格，必须处理的三点

1. **描边粗细**：lucide 默认 `strokeWidth=2`（24 viewBox），缩到 16px 会偏粗、与现有 1px 双色调图标不搭。需在映射组件统一 `strokeWidth={1.5}`（或 `1.25`）。
2. **尺寸**：沿用 `.files-icon` 的 `size-4 shrink-0`，lucide 组件接受 className，无需新增 CSS。
3. **口径统一**：既然文件行换成 lucide，`FolderIcon` 是否也换？——**建议不换**（文件夹开合双形态刚落地、形态表意清晰），但这会造成"文件图标 lucide 描边 + 文件夹自绘双色调"的轻微不一致。可选折中：映射未命中的通用文件仍用现有 `FileIcon`，只在命中类型时用 lucide，差异落在"有类型 vs 无类型"之间，观感反而有层次。

### 4.4 `icon` 属性语义（P1）

| 写法 | 行为 |
|------|------|
| 不写 / `icon="auto"` | 按扩展名自动匹配 |
| `icon="none"` | 不显示图标（行首不留占位，保持 `files-name` 对齐） |
| `icon="<映射键>"`（如 `ts`、`json`） | 强制使用该类型图标 |
| 未知值 | 回退 `auto`，并（可选）产出诊断 `UNKNOWN_ICON` |

改动点：`registry.ts` 的 `File` 加 `attrs: ["name", "href", "icon"]`；`file.tsx` 解析优先级；序列化无需改动（属性透传已验证）。

## 五、成本与体积（实测 + 估算）

| 项 | 数值 | 来源 |
|----|------|------|
| lucide 单图标（ESM 源） | 0.80–1.00 KB | 实测 `dist/esm/icons/file-*.mjs` |
| 10 个图标的源码增量 | ≈ 9 KB（gzip 约 3 KB） | 按单文件估算 |
| 映射表 + 解析函数 | < 1 KB | 估算 |
| lucide 安装体积 | 34.7 MB / 4388 文件 | 实测（**不进产物**，`external`） |
| 方案 C 的数据量级 | 数百 SVG + JSON 清单 | 未在本仓库实测，进入 P2 需先量化 |

工作量：A（映射 + 兜底 + 目验）≈ 0.5 人日；E（属性 + registry + 序列化回归）≈ 0.2 人日；A+B 混合（补 5 个高频自绘双色调）≈ +1 人日。

## 六、风险与未决问题

| # | 风险 / 未决 | 说明 | 建议 |
|---|-------------|------|------|
| 1 | 视觉口径分裂 | lucide 单色描边 vs 现有双色调 | 先只换"文件行"，文件夹保持现状；上线后目验再定 |
| 2 | 16px 下辨识度 | `FileCode` / `FileText` / `FileBraces` 缩小后差异有限 | 优先保证"有类型 vs 无类型"可辨，不追求逐类辨识 |
| 3 | 品牌色诉求 | 若想要 ts 蓝、md 黑、json 黄 | 需按类型注入 `text-*`/CSS 变量，暗色对比度需逐类验；建议不做 |
| 4 | `icon` 与宿主意图冲突 | 宿主可覆盖 `File` 组件 | 属性走 props，覆盖方自然继承；文档需说明优先级 |
| 5 | 依赖升级风险 | 映射依赖 lucide 图标名（`FileJson` 目前是 `file-braces` 的别名） | 只用名字长期稳定的图标；升级 lucide 时跑 `typecheck` 即可暴露缺失 |
| 6 | 体积极端 | 若未来引入整套主题 | 定硬门槛：单次增强产物增量 ≤ 5 KB gzip |
| 7 | 文档缺口 | `registry.ts` 注释提到的 `docs/markdown/02-语法规范.md` 在仓库中不存在 | 若实施 P1，需同步补语法说明或更新注释指向 |

## 七、验证方式（若进入实施）

1. `npm run typecheck`：确保 lucide 图标名与 props 类型正确（缺图标会编译期报错，这是选择 lucide 的额外收益）。
2. `npm run snapshot`：`dev/.out/preview.html` 中逐行核对 `<File>` 是否命中期望图标；往返自检 strict 样例必须仍逐字一致（含新增 `icon` 属性的用例需补 fixture）。
3. 体积：`npm run build` 后对比 `dist/components/index.js` 前后大小。
4. 视觉：静态快照 2 倍图目验亮/暗两套（宿主主题令牌），确认 16px 下不糊、描边不粗。
5. 回退验证：不写 `icon` 的老文章渲染结果与今日**逐像素一致**（除文件行图标外不得有任何布局位移）。

## 八、不改动清单（明确边界）

- 不改 `src/syntax/*`：词法已支持任意属性。
- 不改 `src/serialize.ts` / `jsx-mdast.ts` 的属性序列化逻辑。
- 不改 `registry.ts` 的既有属性语义（仅追加 `icon`，且不写时行为不变）。
- 不引入字体文件、不新增 `@font-face`、不改 `styles/engine.css` 的作用域约定。
- 不动 `<Folder>` 的开合双形态（`docs/文件夹图标开合形态.md` 已实施）。
