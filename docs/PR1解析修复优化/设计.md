## 0. 结论先说

PR #1 修的三处（行内子项、容器内缩进、单行块公式）都成立，但它们只是**三个症状**。把矩阵跑通后，真正的框架缺陷是 6 个，其中 **D1 会丢内容**（比 PR 修的三个都严重），而且 6 个缺陷**全部是跨组件的**——不是某个标签的问题：

| 缺陷 | 影响范围 | 后果级别 |
|---|---|---|
| D1 内容区按行文本扫描，看不见块结构 | **全部 8 个容器 + 7 个子项** | **丢内容 / 结构错乱** |
| D2 行内写法折叠不完整 | 全部带子项的容器（Tabs/Steps/Cards/Accordion/Files/TypeTable） | props 全丢、子项塌陷 |
| D3 缩进与 CommonMark 冲突且修了半途 | 全部容器 | 语义误判 |
| D4 序列化形态单一 + 缩进归一化 | 全部容器 | **往返不保形（这才是「删空格」的真凶）** |
| D5 blocks 索引不覆盖列表/引用内的容器 | 编辑器 | 块索引缺失 |
| D6 深度超限降级成文本 | 全部容器 | 往返结构不等价 |

## 2. 六个框架级缺陷（含证据）

### D1 内容区按「行首文本」扫描，看不见块结构 → 丢内容

词法层的 `lineStart` 只在行首做两件事：匹配 `</Name>`（闭合）、匹配同名 `<Name`（嵌套计数）。它不知道当前行是否处在**围栏代码块 / 缩进代码块**里，于是代码块里的标签照样"生效"。

实测（均由 `dist/` 产物跑出，原文 → 结构 → 往返）：

| 输入 | 解析结果 | 后果 |
|---|---|---|
| `<Callout>` 内含围栏 ```` ```md ```` 内写 `</Callout>` | `jsxBlock(Callout)[code:""]` + 兄弟 `code:"\n</Callout>"` | 容器提前闭合，**代码块内容变成空**，往返后原文彻底变形 |
| `~~~` 围栏内写 `</Callout>` | 同上 | 同样损坏 |
| `<Tab>` 内含围栏内写 `</Tab>` | `jsxBlock(Tab)[code:""]` | 子项被提前截断 |
| 4 空格缩进代码块内写 `</Callout>` | `jsxBlock(Callout)` + 兄弟 `html:"</Callout>"` | 容器当场闭合，内容区为空 |
| 围栏内出现**同名开标签** `<Callout>` | `jsxBlock(Callout)[code:"<Callout>", html:"</Callout>"]` | 嵌套计数器被污染，外层永远等不到自己的闭合 |

这条直接违反策略层写死的承诺（「不崩、**不丢内容**」）。影响全部容器，与组件名无关。

### D2 行内写法由 mdast 补丁实现，覆盖面窄

| 输入 | 结果 | 说明 |
|---|---|---|
| `<Tab value="a" title="x>y">A</Tab>` | `paragraph[html,text,html]`，`Tabs:0` | 折叠用的正则第二份实现（`[^>]*?`）过不了属性里的 `>` → props 全丢 |
| `<Tab value="a">第一段` + 空行 + `第二段</Tab>` | `Tabs:0`，内容变两个段落 | 折叠只在「同一个段落」内生效 |
| `<TypeItem ...>第一段` + 空行 + `第二段</TypeItem>` | `TypeTable:0` | 同上 |

注意：**mdast 层本来是正确的折叠位置**（只有它能看见代码 span 这类行内结构，词法层看不见）。问题不在层次，在两处：折叠范围只有段落、标签解析有两份实现。

### D3 缩进：与 CommonMark 冲突，PR 只修了一半

| 输入 | 现状 |
|---|---|
| `<Callout>` 内正文缩进 4 | `code:"正文"`（CommonMark 语义，缩进即代码） |
| `<Folder>` 内正文缩进 4 + 子项缩进 4 | 正文 `code`、子项正常 → 相对缩进被打断 |
| 子项用 tab 缩进 | 探针吃掉了 tab，但子文档仍判成缩进代码 → `Tabs:0`，`<Tab ...>` 变 code |
| 缩进容器内的 8 空格代码块 | 标签行去了缩进、代码行没去 → 代码内容多出 4 空格（内容被改写） |

结论：现在的实现既不是纯 CommonMark，也不是自洽的缩进模型，属于「半途」。**继续在这条路上加分支就是补丁**——缩进必须先定政策（见 §4）。

### D4 序列化形态单一 + 缩进归一化 → 往返不保形（「删空格」的真凶）

用户说的「不要影响入库往返」正在这里：

- 行内写法存回一律变块形态：`<Tab value="npm">npm install</Tab>` → `<Tab ...>\n\nnpm install\n\n</Tab>`；
- 容器内所有缩进一律被抹成 0 列（`<Files>` 里 4 空格缩进的 `<File />` 存回变顶格）。

也就是说，**即使解析侧不动一个空格，序列化侧也已经在删空格**。要真正兑现往返保真，得在序列化侧解决（§5.3），解析侧删缩进只是把这个缺陷藏起来。

### D5 blocks 索引不覆盖列表 / 引用内的容器

`extractBlocks` 只把顶层 children 映射成块，遇到 `list` / `blockquote` 就当成一个 `visual` 块停下。实测「列表内的 `<Files>`」返回的 blocks 里**没有任何容器信息**，编辑器拿不到子项区间。且 `对接契约.md` §4.5 写「写在列表项内的容器 → `source`（reason `list-context`）」，与实际解析（正常成容器）不一致。

### D6 深度超限降级成文本 → 往返结构不等价

四层嵌套 → 第 4 层被降级成 `text`（原文串）。再解析时那段文本又被识别成容器，于是 `roundtrip` 之后结构与首次不同（矩阵里唯一「结构等价=否」的一例；幂等仍成立）。降级策略应改为「保留节点 + 标记 degraded」，而不是把结构拍成文本。

## 3. 设计原则

1. **不猜、不改写**：解析器不替用户重排缩进、不删空白、不改内容。
2. **单一事实来源**：标签解析（开/闭）、形态判定、组件清单各只有一处；全部 8 个容器 + 7 个子项由 `registry.ts` 驱动，不写 `if (name === "Tab")` 这类分支。
3. **符合分层**：词法层只处理它看得见的东西（行结构、围栏状态），行内结构相关的判断留在 mdast 层。
4. **往返是硬约束**：能解析的必须能原样写回（形态 + 缩进）；做不到就给诊断，而不是悄悄改。
5. **修复要跨越组件**：每条修复的验收用例至少覆盖 3 个不同容器，防止「只修 Tab」。

## 4. 缩进政策（必须你定，两案都不含「删空格」）

**政策 A：缩进不参与语义（推荐先落这个）**

- 撤销 PR 的去缩进探测，恢复纯 CommonMark：`4 空格 = 缩进代码块`；
- 对「容器内容里 ≥4 空格缩进且行首是已知标签」产出诊断（如 `INDENT_AS_CODE`：该行会被当成代码块，建议顶格），**提示而不改写**；
- README / 对接契约明确：容器内容顶格书写（≤3 空格无害），代码用围栏；
- 序列化保持顶格输出（与今天一致）。
- 代价：没有「美观缩进」。但你要求的「不删空格、不改内容」在 A 下 100% 成立。

**政策 B：缩进即排版（往返保真版，工作量大）**

- 缩进按「内容列前缀」理解（与 CommonMark 对 list item 的内容列同一语义）：基准 N = 内容首行缩进，N 是从行首消费掉的前缀，不计入内容；
- **关键补充**：容器节点记录 `indent: N`，序列化时按 N 逐层还原子节点缩进 → 入库往返保形，不再"删空格"；
- 需要改：词法基准 + 序列化逐层缩进 + `blocks` 区间 + 诊断口径 + 编辑器滚动同步。
- 代价：语义自造（偏离纯 CommonMark）、实现量大、需要一套新的回归断言。

我的建议：**先 A 再议 B**。A 已经把「看起来不对」的多数场景收敛为「明确的诊断 + 规范的写法」，且零语义发明；B 应作为独立需求立项，不和这次修复混做。

## 5. 各缺陷的修复设计

### 5.1 D1：围栏感知 —— **已撤回（不是缺陷）**

用户定规则：**行首 `</Name>` 就是容器结束**，代码块（``` / ~~~）里同样如此，不做围栏豁免。

- 围栏豁免方案（本节旧内容）已从 `jsx-flow.ts` 整段删除；
- 契约已改为「行首 `</Name>` 即闭合，围栏不例外」，并写进 `对接契约.md` §4.5；
- 由此带来的一致性要求：想演示 `</Callout>` 字样时，不要把闭合标签放在行首（可写成行内代码 `` `</Callout>` ``，实测不受影响）。

### 5.1.1 事故记录：dev 白屏（缩进探测违反 micromark 契约）

dev 页整页白屏，根因不在围栏，而在 PR #1 引入的**缩进探测** `tokenizeIndentTag`，两处违反 micromark 的调用契约：

| 违规 | dev 断言 | 触发条件 | 修法 |
|---|---|---|---|
| `enter` 之后只 `return indentSpace`，本轮一个字符都没消费 | `expected character to be consumed` | 容器内容的第一行就会触发 | `return indentSpace(code)`，同一轮内消费（与 micromark 的 `factorySpace(...)(code)` 写法一致） |
| 顶格行（缩进 0）也 `enter` 了探测 token，随后 `exit` 一个空 token | `expected non-empty token` | 子项顶格书写（最常见写法） | 没有缩进就直接 `nok`，不进探测 |

为什么自检没抓到：`dist` 是生产构建，断言被裁掉；dev 用 micromark 的 development 构建才带断言。

因此定为验收口径（临时探针脚本用完即删，不留在仓库）：改解析器后除了 `npm run selfcheck`，还要**在 dev 构建下真跑一次**——打开 dev 页确认渲染、并对四篇 fixture 各解析一遍，两者都无断言才算通过。

### 5.2 D2：折叠补全（保留在 mdast 层，做完整）

- 标签解析唯一化：删除 `jsx-inline.ts` 里的 `OPEN_TAG_RE`，统一走 `parseOpenTag`（顺带统一名字字符集）；
- 扫描单位从「段落」提升到「父节点子序列」：从第 i 个子节点开始，允许跨段落、直到找到匹配闭标签；遇到非段落兄弟立即放弃（不做跨结构猜测）；
- 跨段落折叠出来的节点形态记为块（序列化走块形态），props 与子内容照常可得；
- 由注册表驱动，所有带子项的容器自动覆盖；
- 验收：属性含 `>`、子项含空行、多行内容三类用例在 Tabs / Steps / TypeTable 三个容器上全部通过。

### 5.3 D4：序列化保形，不再凭空加空行（已定，本轮做）

**结论依据**：实测无空行的列表 / 表格 / 引用 / 标题 / 围栏五种块级内容都能正常解析、正常闭合（见 `矩阵结果.md` §5 与本节表格），契约 §188 也写明「语法不要求空行」。既然解析不需要，序列化就不该强行加——用户原话「能够正常解析，那就别莫名其妙加空行」。

规则（全部由 `position` 推导，不新增任何标志字段）：

| 情形 | 判定 | 输出 |
|---|---|---|
| 内容与开标签同一行 | `children[0].position.start.line === node.position.start.line` | 行内形态 `<X a="b">内容</X>` |
| 开标签与内容之间 | `children[0].start.line - node.start.line` | `=1` → 单换行；`>1` → 一个空行（保形） |
| 内容与闭标签之间 | `node.end.line - lastChild.end.line` | `=1` → 单换行；`>1` → 一个空行（保形） |
| 子项之间 | `right.start.line - left.end.line` | `=1` → 单换行；`>1` → 一个空行（保形） |
| 无子节点 | `children.length === 0` | `<X a="b"></X>`（写进契约） |
| 节点无 position（宿主自建） | — | 回退为规范形态 `<X>\n\n内容\n\n</X>`，保证可读 |

实现要点：

1. 子项之间不能再用 `state.containerFlow`（它固定用空行连接，且 `mdast-util-to-markdown@2.1.2` 的 `Options.join` 并未生效）：在 handler 内自己遍历 `children`，用 `state.handle` 逐个序列化后按上表拼分隔符（约 20 行，`state.indexStack` 与 tracker 照 `container-flow.js` 的写法处理）。
2. 首尾空行交给同一个函数，三种形态（行内 / 紧凑 / 有空行）统一产出。
3. `normalizeMarkdown` 继续承担「格式化」职责（补空行、收敛空行）——想统一成规范形态时用它，`serialize` 不再兼职。
4. 契约改动：§257「容器输出形态固定」改为「serialize 保形；规范形态由 `normalizeMarkdown` 产出」，§258「空行数量收敛为 1」归 `normalizeMarkdown`；验收 §354 的 `roundtrip(md) === md` 从「7 个组件样例」扩展为「矩阵全部用例（除 GFM 表格分隔符、强调符号等既有规范化外）逐字节相同」。
5. 边界与风险：
   - 紧凑形态下闭标签紧跟列表 / 表格 / 引用 / 标题 / 围栏 → 已实测均可正确闭合；S6 里逐个构造加断言，若个别构造不稳定，只在该构造后补一个空行（局部规则，不做全局回退）；
   - `<Tab>a` + 换行 + `b</Tab>` 这类「开标签同行、闭标签不同行」的写法：按首行判定为行内形态，内容里的换行作为文本换行保留（写断言）。

### 5.4 D5：blocks 索引递归

- `extractBlocks` 对 `list` / `blockquote` 等容器型 visual 块递归，产出带层级的块列表（或扁平 + parent 字段）；
- 契约 §4.5 的 `list-context` 行改为实际行为（列表内容器正常解析，编辑器可见）。

### 5.5 D6：降级保留节点

- 超限层不再替换成 `text`，改为保留 `jsxBlock` + `data.degraded = true`：渲染按源码块展示（与今天视觉一致），序列化原样输出；
- 验收：四层嵌套的 `roundtrip` 结构等价（当前为「否」）。
